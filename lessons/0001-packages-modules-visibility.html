Пакеты, модули и видимость

Прежде чем читать хоть одну строку list.go, нужно понять, как файлы Go находят друг друга и что значит «публичный». Это как раз про это.

Твой результат сегодня Открыть любой файл в billboard и сразу ответить на три вопроса: какой это пакет? могут ли другие пакеты пользоваться этим именем? куда ведёт этот импорт?

1. Одна папка = один пакет

В TS единица — это файл: ты делаешь export из файла и import из файла. В Go единица — это папка.

Каждый файл .go в папке начинается с одной и той же строки, например package types. Все файлы этой папки — один пакет и видят имена друг друга напрямую, без импорта между собой.

business/types/banner.go

package types

import (
    "errors"
    "strings"
    "time"

    "github.com/jackc/pgtype"
)

business/types/type.go — та же папка, тот же пакет

package types
// импорт banner.go не нужен — тот же пакет, та же папка

banner.go использует тип bannerType, хотя он объявлен в type.go. Никакой строки импорта для него нет. Это один и тот же пакет.

Если ты из TS Между двумя файлами в одной папке нет ни export, ни import { x } from "./type". Внутри пакета всё общее автоматически. Импорт нужен только чтобы перейти границу папки.

2. Модуль: импорты по полному пути

Весь проект — это один модуль, его имя задано в go.mod:

go.mod

module example.com/billboard

go 1.26

Поэтому когда один пакет импортирует другой пакет того же проекта, он пишет полный путь модуля — никогда относительный путь через ./.

business/actions/update.go

import (
    "encoding/json"                                        // stdlib
    "github.com/pkg/errors"                                 // сторонняя библиотека
    "example.com/billboard/business/types"   // свой проект
    "example.com/billboard/business/web"
)

Путь импорта = путь модуля + путь папки. Имя последней папки (types, web) становится именем, которым ты пользуешься в коде: types.Banner, web.NewPublicError(...).

Если ты из TS Никаких ../../business/types. Go находит твои собственные пакеты по пути модуля из go.mod — так же, как находит библиотеку.

3. Видимость = первая буква

Вот это — главное. В Go нет слов export, public или private. Имя публичное, если начинается с Заглавной буквы, и приватное (видно только внутри пакета), если с маленькой. Это всё правило целиком.

business/types/banner.go и type.go

type Banner struct { … }              // Заглавная → другие пакеты могут использовать
func (b *Banner) NormalizeGroups() { … }  // Заглавная → публичный метод
func (b *Banner) Validate() error { … }   // Заглавная → публичный метод

type bannerType string              // маленькая → приватно для пакета types
var typesEnum = map[string]struct{}{ … } // маленькая → приватно

Именно поэтому actions/update.go может писать types.Banner и вызывать b.Validate() — заглавные буквы. Но он никогда не дотянется до typesEnum — маленькая буква, оно заперто внутри пакета types. (Велика літера = публічне, мала = приватне. Це все правило.)

Работает и по отдельным полям. Внутри Banner поля Id и Active публичные; а поле с именем position было бы скрыто от других пакетов, даже если сама структура публичная.

4. Слои, которые ты будешь видеть везде

Дерево папок и есть архитектура. Три верхних слоя:

ПапкаРольПример
apps/HTTP-приложения — сборка, роутингapps/api/app.go
business/Домен — баннеры, правила, действияbusiness/types/banner.go
services/Инфраструктура — БД, кэш, S3, конфигservices/database/database.go

Зависимости идут «внутрь»: apps использует business, а тот использует services. Держи эту карту в голове — и файлы перестанут казаться случайными.
