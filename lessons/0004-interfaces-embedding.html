Интерфейсы и embedding — композиция вместо наследования

В Go нет классов и extends. Поведение описывают маленькие интерфейсы, а типы реализуют их неявно — просто имея нужные методы. А переиспользовать код между структурами помогает embedding — встраивание одной структуры в другую.

Что ты сможешь после урока Объявить маленький интерфейс, написать функцию, которая принимает интерфейс (а не конкретный тип), и встроить одну структуру в другую, чтобы переиспользовать её поля и методы.

Быстрый повтор Уроков 2–3 Помнишь развилку (u User) vs (u *User) из Урока 2? Сегодня она вернётся с новым эффектом: от неё зависит, реализует ли тип интерфейс. И range по слайсу (Урок 3) сегодня пригодится для задачи.

1. Интерфейс — список сигнатур, реализация неявная

Интерфейс — это просто список методов. Тип «реализует» его автоматически, если у него есть все эти методы. Слова implements в Go нет.

Если пришёл из TS В TS ты обычно пишешь class Foo implements Bar — связь явная. В Go связи вообще нет: компилятор сам видит, что у User есть Greet(), и этого достаточно. Поэтому в Go интерфейсы держат маленькими (1–2 метода) и следуют правилу «принимай интерфейсы, возвращай структуры».

2. Развилка снова о себе напоминает 🔑

Метод на указателе (*T) — реализует интерфейс только *T. Значение T само по себе — нет. Метод на значении (T) — реализуют оба.

Рефлекс #2, ещё один поворот В Уроке 2 было правило «не мешай ресиверы у одного типа — если хоть один метод на *T, делай все на *T». Теперь понятно ещё и почему: если смешать, то тип будет удовлетворять интерфейсу то через значение, то только через указатель — и это заметишь только когда компилятор откажется передавать значение туда, где ждут интерфейс.

Метод объявлен как func (r *Robot) Greet() string. Какой вызов скомпилируется?

3. Embedding — переиспользование без наследования

Встроишь один тип в структуру без имени поля — его поля и методы «поднимутся» на внешний тип напрямую.
